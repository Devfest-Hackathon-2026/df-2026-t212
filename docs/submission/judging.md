# 審査基準への応答

このページは、After Hueの実装を審査の4項目に沿って確認するための案内です。評価を主張するだけでなく、何を見ると確かめられるかを記載しています。基準は参加者から共有された大会説明の要約に基づいています。

## 1. Google技術の活用

AIのリクエストをCloud Runで受け、Firebase Authenticationで本人の匿名IDを確認し、Firestoreで利用回数を予約してから、Vertex AIのGeminiへ渡します。AIが呼び出す採色・範囲指定・描画などのツールは端末で動きます。画面と共通編集処理にはFlutterとDartを使っています。

この分担により、AIの認証情報と利用制限をサーバー側に置きながら、元の写真と高解像度の描画処理は端末で扱えます。Firestoreのトランザクションは、サーバーの再起動や複数インスタンスでも利用上限を共有するために使っています。Google Cloudは、編集判断を届ける経路と、その認証・利用量管理を担います。

Cloud Runへの配置、Firebase匿名認証、未認証リクエストの拒否、Vertex AIによる写真の選別を実接続で確認しました。現像では途中画像を二度確認し、追加の編集依頼でも色とトーンを変更して、端末側の描画まで完走しました。[実接続の記録](verification.md)に確認内容をまとめています。一枚の確認を、全写真・全端末の動作保証とはしていません。

確認先: [構成図・サービスの役割・実接続の状態](architecture.md)、[AIクライアント](../../lib/agent/gemini_agent.dart)、[AIサーバー](../../server/ai/README.md)、[ヘルスチェック](https://after-hue-ai-675070172838.asia-northeast1.run.app/health)。

## 2. プロダクトの完成度

写真を取り込み、Autoまたは手動で現像し、ギャラリーと地図で見返し、共有・印刷用画像にする流れを実装しています。各画面の完成だけでなく、複数枚の取り込み、待機中の表示、処理中の削除、編集を続けたまま画面を離れる場合も扱っています。

AIが変更するのは、手動編集でも扱う編集設定です。描画は共通のレンダラーで行うため、AIの提案を保存した後も人が調整できます。元の写真と編集設定を分け、色の除外や範囲指定などの操作を個別に検証できる構成にしました。

自動テストには、処理の中止、複数選択、原本の更新、似た写真のグループ化、色の除外、Crop、印刷などが含まれます。検証結果は各テストと[設計・表示確認の記録](../../design-qa.md)で追えるようにしています。これは全端末での動作保証や、物理プリンターでの印刷品質を意味するものではありません。設計を変えた理由と具体的な確認先は、[実際の利用から変えたこと](design-decisions.md)にまとめています。

確認先: [デモの構成](demo.md)、[テスト一覧](../../test/)、[印刷の確認記録](../../design-qa.md)、[処理中断のテスト](../../test/agent_cancellation_test.dart)、[画面を離れた編集のテスト](../../test/background_activity_test.dart)。

## 3. 社会課題への解決力

対象は、標準カメラなどで日常的に写真を撮り、その写真を後から別の形でも楽しみたい人です。毎回編集アプリを開いて写真を選ぶ作業は、普段の撮影とは分かれがちです。After Hueでは、許可された写真の自動取り込みと現像、処理結果へ戻れるActivityによって、その作業を減らすことを狙っています。

色を残す表現は、元の写真の被写体や構図を保ちます。さらに写真由来の色バッジを一覧と地図で使うことで、写真の個性を見返す手がかりにします。自動処理の結果を本人が直せることと、気に入った一枚を印刷用画像にできることも、この体験につながります。

課題の根拠は開発者の体験と開発中の操作です。社会全体での問題の大きさや、利用頻度が増える効果を示す調査は行っていません。評価していただきたいのは、この具体的な利用場面に対して実装がどう応えているかです。現在の提出原稿で選択されているカテゴリは、エンターテインメントです。

確認先: [課題設定と主張の範囲](problem.md)、[具体的な利用場面](product.md#どのように使うか)、[人とAIの役割](product.md#aiに任せること人が決めること)。

## 4. ピッチの構成と説明力

デモでは、一枚の写真を最初から最後まで追います。普段撮った写真の取り込み、Autoの結果、本人による修正、写真の蓄積、印刷という順です。同じ写真を使うことで、画面ごとの機能紹介にならず、何ができるようになったかを追える構成にします。

AIの待ち時間を編集で短縮する場合は、倍速や省略を画面で明示します。端末内の処理とクラウドAIへの問い合わせを区別し、生成したデモ写真を実際の撮影記録として紹介しません。デモの最後には、現時点で使える機能と、今後の構想を分けて示します。

確認先: [読み上げと画面操作の案](demo.md)。完成した動画と提出用スライドのリンクは、まだこの資料に紐づいていません。

## AIをどこで、なぜ使ったか

プロダクトでは、写真の主役を解釈し、残す色や範囲を決める部分にクラウドAIを使っています。主役の判定は色の頻度だけでは決めにくく、「この色を消したい」という言葉を編集操作に結び付ける必要もあるためです。一方、画素の加工、色の比較、キャッシュ、重複判定、原本変更の比較は、決められた手順で動く端末内の処理を中心にしています。

開発時にはAIコーディング支援と画像生成を使っています。実装の補助、問題の切り分け、テスト、画面案の比較に利用し、どの案を採用するか、どの操作を残すかは開発者が判断しました。印刷の組版では、生成した複数案を比較し、選んだ案を実際の描画処理へ落とし込んだ後、文字やバッジの大きさ、行間を実画面で調整しています。

## 開発を通じた学び

色が近いことと、同じものを残したいことは一致しません。ピンクを残そうとするとオレンジまで残る、といった実際の写真での問題から、残す色だけでなく除外する色、明るさや彩度の条件、対象の範囲を組み合わせる設計になりました。

また、処理が完了するまでの途中状態が使いやすさを左右しました。結果が正しくても、削除した写真が残って見える、待機中なのか分からない、画面を離れた後に結果へ戻れないと、利用者は次の操作を選べません。状態表示やActivityを実装し、写真単体の仕上がりと一連の操作を一緒に検証するようになりました。

ここに記載した学びは、開発中に報告された問題と、それに対応する実装に基づくものです。一般の利用者全体についての調査結果ではありません。
