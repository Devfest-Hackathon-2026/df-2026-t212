# 審査基準への応答

このページは、After Hueの実装を審査の4項目に沿って確認するための案内です。評価を主張するだけでなく、何を見ると確かめられるかを記載しています。基準は参加者から共有された大会説明の要約に基づいています。

## 1. Google技術の活用

現時点で確認できるGoogle由来の基盤は、アプリの画面と共通処理を実装しているFlutterとDartです。同じ編集データと描画処理をiOSとAndroidで共有しつつ、カメラや物体抽出のような端末固有の機能はネイティブ実装に分けています。

ただし、Flutterを使っていることだけでは、大会で指定されたクラウド実行基盤の利用条件を満たした説明にはなりません。現在のクラウドAIはOpenAI API、地図はMapLibreとOpenFreeMapです。Cloud RunやFirebase Hosting等の稼働は、この資料作成時点では未確認です。

ExploreはGCPを使う機能として別ブランチで開発します。最終版では、実際に利用したサービス、ユーザーの操作から呼ばれる経路、そのサービスを選んだ理由、稼働URLを[技術構成](architecture.md)に追加します。エージェントのGoogle Cloud移行は別の判断として保留しています。実装と稼働を確認するまでは、Google技術が中核を担っているという実績として記載しません。

確認先: [依存関係](../../pubspec.yaml)、[実行時のエージェント選択](../../lib/data/store.dart)、[現在のAI実装](../../lib/agent/openai_agent.dart)。

## 2. プロダクトの完成度

写真を取り込み、Autoまたは手動で現像し、ギャラリーと地図で見返し、共有・印刷用画像にする流れを実装しています。各画面の完成だけでなく、複数枚の取り込み、待機中の表示、処理中の削除、編集を続けたまま画面を離れる場合も扱っています。

AIが変更するのは、手動編集でも扱う編集設定です。描画は共通のレンダラーで行うため、AIの提案を保存した後も人が調整できます。元の写真と編集設定を分け、色の除外や範囲指定などの操作を個別に検証できる構成にしました。

自動テストには、処理の中止、複数選択、原本の更新、似た写真のグループ化、色の除外、Crop、印刷などが含まれます。全体テスト71件通過の記録に加え、用紙方向と大きな文字設定の修正後には印刷関連10件を確認しています。これは全端末での動作保証や、物理プリンターでの印刷品質を意味するものではありません。設計を変えた理由と具体的な確認先は、[実際の利用から変えたこと](design-decisions.md)にまとめています。

確認先: [デモの構成](demo.md)、[テスト一覧](../../test/)、[印刷の確認記録](../../design-qa.md)、[処理中断のテスト](../../test/agent_cancellation_test.dart)、[画面を離れた編集のテスト](../../test/background_activity_test.dart)。

## 3. 社会課題への解決力

取り組む課題は、日常で心が動いたものを、自分の表現として残すまでにかかる編集の手間です。対象は、散歩や旅行、普段の暮らしで写真を撮り、気に入った一枚を自分なりに仕上げたい人です。撮影時に惹かれた色を選び、周囲との関係を調整する作業を、写真上の操作とAIの補助で支えます。

狙っているのは、専門的な画像編集の操作を覚える前に、自分が見つけた色を作品として残せることです。自動処理の結果を修正できるため、何を主役にするかという本人の意図も保てます。印刷用画像の作成は、画面の中の写真を手帳や身近な場所へ持ち出すための出口です。

日常の体験を表現する機会を広げることに、社会的な意義があると考えています。これは現時点ではプロダクトの仮説です。利用頻度や編集時間についての定量的な効果はまだ測定していません。カテゴリは「クリエイティブ」が内容に対応しますが、登録・提出時に選択したカテゴリは別途確認が必要です。

確認先: [課題設定と主張の範囲](problem.md)、[具体的な利用場面](product.md#どのように使うか)、[人とAIの役割](product.md#aiに任せること人が決めること)。

## 4. ピッチの構成と説明力

デモでは、一枚の写真を最初から最後まで追います。撮影または取り込み、Autoの結果、本人による修正、写真の蓄積、印刷という順です。同じ写真を使うことで、画面ごとの機能紹介にならず、何ができるようになったかを追える構成にします。

AIの待ち時間を編集で短縮する場合は、倍速や省略を画面で明示します。端末内の処理とクラウドAIへの問い合わせを区別し、生成したデモ写真を実際の撮影記録として紹介しません。デモの最後には、現時点で使える機能と、今後の構想を分けて示します。

確認先: [読み上げと画面操作の案](demo.md)。完成した動画と提出用スライドのリンクは、まだこの資料に紐づいていません。

## AIをどこで、なぜ使ったか

プロダクトでは、写真の主役を解釈し、残す色や範囲を決める部分にクラウドAIを使っています。主役の判定は色の頻度だけでは決めにくく、「この色を消したい」という言葉を編集操作に結び付ける必要もあるためです。一方、画素の加工、色の比較、キャッシュ、重複判定、原本変更の比較は、決められた手順で動く端末内の処理を中心にしています。

開発時にはAIコーディング支援と画像生成を使っています。実装の補助、問題の切り分け、テスト、画面案の比較に利用し、どの案を採用するか、どの操作を残すかは開発者が判断しました。印刷の組版では、生成した複数案を比較し、選んだ案を実際の描画処理へ落とし込んだ後、文字やバッジの大きさ、行間を実画面で調整しています。

## 開発を通じた学び

色が近いことと、同じものを残したいことは一致しません。ピンクを残そうとするとオレンジまで残る、といった実際の写真での問題から、残す色だけでなく除外する色、明るさや彩度の条件、対象の範囲を組み合わせる設計になりました。

また、処理が完了するまでの途中状態が使いやすさを左右しました。結果が正しくても、削除した写真が残って見える、待機中なのか分からない、画面を離れた後に結果へ戻れないと、利用者は次の操作を選べません。状態表示やActivityを実装し、写真単体の仕上がりと一連の操作を一緒に検証するようになりました。

ここに記載した学びは、開発中に報告された問題と、それに対応する実装に基づくものです。一般の利用者全体についての調査結果ではありません。
